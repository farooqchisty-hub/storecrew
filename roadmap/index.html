How we build it, in what order, and what it costs to run

The recommendation, not a menu. Cloud is the destination, the Mac is only where V1 is tested. Simple and boring wins every tie. Companion: How the crew is wired (diagrams).

01Codex

Recommendation

Your instinct is right. Build the runtime one way, here. Splitting the runtime path across two coding agents to save tokens buys a merge problem, two mental models of the same system, and a fail-closed approval path that nobody owns end to end. The only work that survives the test of "genuinely siloed, finishes cleanly, hands back a finished artefact I consume" is three tasks with a schema-defined boundary: the dashboard frontend built against the Worker's OpenAPI spec, the conversion of the 330-checkpoint workbook and the ad concept libraries into their JSON schemas, and the port of the forked Advise-mode skill libraries into agents/*/assets. Those three can go to Codex in parallel if you want to spend those tokens. Nothing on the runtime, gateway, approval or brain path does. The build pack in storecrew-app stays valid as the specification regardless of who types.

02Shopify access, the real answer

Definitive, from live shopify.dev today

For our model, no Shopify review and no protected-data review. We create one app per merchant in our Dev Dashboard with custom distribution, generate an install link for that merchant's store, and they click it. Shopify's distribution table for custom distribution reads "Approval required: No", and the protected customer data table reads "Custom app: Always available" for both Level 1 and Level 2. The merchant sees a standard permissions screen and clicks Install. Two to three minutes on their side, no token copying, nothing to configure.

What is dead, and what does not help

  • Merchant-created tokens are gone. "You can no longer create new admin-created custom apps. Existing apps are unaffected and continue to work. For new apps, use Dev Dashboard or Shopify CLI." Our earlier Level 3 design assumed a merchant pastes a token. It cannot happen any more.
  • Client credentials grant does not cross organisations. "Client credentials can't reach a store outside your organization, including a client's store." It is for your own stores only.
  • The one merchant-self-serve variant (they create the app in their own Dev Dashboard and hand us a client id and secret) is undocumented for live merchant stores and puts credentials in their hands. Not building on it.

03Architecture recommendation

Everything below is already specified in storecrew-app/specs/. This is the why.

Runtime

ConcernDecisionWhy this and not something cleverer
Where agents executeOne Node 22 process on one Hetzner VM (CPX31, about 14 euros a month), no inbound ports, pulling jobs from a Cloudflare QueueWorkers cannot run a ten-minute loop with image rendering in it. A VM can, and one process is the easiest thing in the world to reason about. Cloudflare Containers later is a contained migration because the queue contract does not change
How they are triggeredThree triggers, one path: owner message via the Operator, Cron Trigger every 15 minutes for Hosted schedules, approval resume. All become a RunInput on the queueOne dispatch function, one cap check, one idempotency key. There is no second way to start a run
How they hold stateThey do not. The runner is stateless between pulls. A run that needs approval ends; the resume is a new run carrying resume_from. State lives in D1 (runs, approvals, events), R2 (outputs, brain), and one Durable Object per customer for conversationKill the VM mid-run and exactly one run completes. That property is worth more than any framework feature
The agent loopOurs, roughly 400 lines, provider-agnostic behind one interface. No Claude Agent SDK, no LangGraphOur agents have fixed tool lists and bounded runs. We lose nothing, and we own the approval gate, which is the one thing that must never live in someone else's library
DurabilityCloudflare Queues with retries and dead-letter, plus the idempotency keyTemporal is the fully-MIT escape hatch if a multi-day run ever appears. It has not

Multi-tenancy, designed in on day one

  • Every table except customers and agents carries customer_id, every query filters on it, and a test introspects the schema to prove it. There is no cross-customer read path to retrofit later.
  • One Durable Object per customer for conversation state and the approval lock. Tenants cannot share a DO by construction.
  • R2 keys are prefixed by customer. Signed URLs only, 15-minute expiry. The bucket is private.
  • Shopify: one app per customer at launch (see section 02), so a token cannot be valid for two stores.
  • Every /api/* route returns 404, never 403, for another tenant's id. We do not confirm existence.
  • Agents share state only through the brain, and the brain is per customer. Agents never call each other.

Secrets

  • Per-customer credentials live in one AES-GCM encrypted blob per customer in D1, keyed by a master key in Cloudflare Secrets Store. The runner fetches a credential per run over an authenticated internal endpoint, holds it in memory for the run, and zeroes it. It never lands on disk.
  • The runner has exactly two credentials of its own: the Cloudflare API token for queues and R2, and the model key.
  • Prompts never contain credentials. Tools take a ctx.secret(kind) accessor; the model sees tool names and arguments, not keys.
  • Logging redacts any key matching token, secret, key, password, authorization, and any value matching known key prefixes. A CI test greps captured logs for every fixture secret.
  • Rotation: revoke and relink a connector from the dashboard. Shopify offline tokens rotate by reinstall. The master key rotates by re-encrypting blobs in a migration.

API surface

One Worker, one Hono app. The dashboard and any future client call the same /api/* routes behind a magic-link session cookie. Channels arrive at /webhooks/*. The public activity feed is /public/activity. The runner talks to the Worker only through /internal/* with a runner token. Nothing calls the VM. Full route table in SPEC-02.

Observability without a terminal

  • Every state change is an events row. The dashboard timeline, the activity strip, the Monday brief and the ops alerts are all views over that one table.
  • Ops alerts land in a Telegram chat you already have open: dead-letter arrival, approval token mismatch, connector failure, runner heartbeat missing for five minutes, any customer hitting monthly cap before day 20, provider error rate over 10 percent. One alert per condition per hour.
  • /health is green or red. /ops shows gross margin per customer. If you never open a terminal after deploy, nothing is hidden from you.

Over-engineering I am flagging, including things asked for
  • Cloudflare Containers or Workflows for the agent loop now. One VM and a queue is simpler and identical in behaviour. Revisit at 200 customers.
  • A vector database for the brain. Markdown in R2 with a D1 index was independently validated over every option. Add semantic recall only when a real query fails without it.
  • WhatsApp at launch. Telegram proves the entire interaction model in two days with no gatekeeper. WhatsApp is an adapter behind a Meta review we start on day one and ship when it clears.

  • Self-serve signup for Motion B. You said it yourself: premature. Twenty hand-onboarded customers first.

06The two motions, refreshed

Motion A, the digital product

What changes against the earlier ideation, now that Hosted is real and the Advise mode exists as a first-class thing: the DIY tier is Advise mode itself. Every agent already has a mode that runs on the buyer's own ChatGPT or Claude with zero credentials. That is the product. It is not a separate build.

TierWasNowFormat
One, DIYSkill files plus a brain the buyer buildsAll sixteen agents in Advise mode plus the Brain Builder, installable in their own AI. Their tokens, their toolingSkill bundles (below)
TwoWe connect their tools with them in a walkthroughSame bundle plus the Act-mode tool wiring as install recipes, plus a 90-minute walkthrough where we connect their keys. They run it, on their keysBundle plus session
ThreeDone for you, monthlyIs Hosted. Tier three of Motion A and the product of Motion B are the same system. Motion A's landing page sells it as the top rung; Motion B sells it as the whole product to a different audienceHosted

Format for the DIY tier, recommended and defended: Agent Skills bundles to the agentskills.io open standard. One folder per agent: SKILL.md, assets/, examples/, manifest.json, shipped under .agents/skills/ and mirrored to .claude/skills/. Why: one tree installs into Claude, Claude Code, Codex, Cursor, Antigravity and OpenCode without conversion; npx skills add is the distribution channel and the skills.sh leaderboard is free traffic; the same AGENT.md that runs on our cloud is the SKILL.md in the bundle, so the DIY product and the Hosted product are literally the same files at different modes, and there is nothing to keep in sync. The alternative, a zip of prompts and PDFs, is what every competitor sells and what buyers do not open.

Motion B, the hosted solution

Sold as one solution customised per store, in the Runneth frame: the brain for your store, and the crew that runs on it. Never the word retainer. The customisation is real and cheap: the brain is per store by construction, and the three-agent bundle is chosen per store on the onboarding call. Hand onboarding for the first twenty means a 60-minute call where we build the brain live, connect Shopify, run Store Fix while they watch, and leave the trial pair running. Self-serve waits until twenty customers have taught us what the call needs to cover.
