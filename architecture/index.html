01The system at a glance

Seven layers. A message enters at the top, work happens in the middle, results land in storage and come back as a notification. The brain sits beside every layer, because every agent reads it before acting and writes to it after. This diagram is the corrected one: three boxes on the old version described things the code does not do.

The four design rules the whole thing rests on

The Operator never does domain work. It plans, routes, collects approvals and compiles the brief. Specialists do the work. That keeps the one component every request passes through small, testable and boring, which is exactly what you want it to be.

Every action that costs money or touches a customer passes an approval gate that fails closed. Expired, malformed or missing approval means nothing happens and the agent asks again. There is no path where silence becomes consent, and the single-use rule is enforced twice: by a conditional UPDATE and by a database trigger that refuses a second use of a token.

The brain is the only shared state between agents. Agents never call each other. Creator Outreach does not tell Ad Creative which content came in; it writes to the brain, and Ad Creative reads it. That is what makes agents independently deployable and independently sellable.

The interface is generated from the contract, never hand-written per agent. Sixteen hand-built screens diverge inside a month. One renderer reading seventeen manifests cannot.

02The two front doors

There is one application. A person signs in once, with an email and no password ever, and the session they get back carries a role. Admin sees the console. An owner sees their store. Nothing about this is two products, and nothing about it is a permissions matrix waiting to be got wrong.

The rules, stated once so they are not re-litigated

RuleHow it is enforcedWhy it is this way
No passwords, anywhere, everThere is no password column and no password endpoint. Sign in is a link in an email and nothing elseNothing to leak, nothing to reset, nothing to reuse from another breach. A merchant who forgets a password never contacts support
Only the hash of a sign-in token is storedSame pattern as approvals and downloads, both of which store token_hash and never the token. Reissuing rotates the hash, so an old link dies the moment a new one is mintedA stolen database gives an attacker nothing that can be replayed
Fifteen minute expiry, single useExpiry checked on exchange; use recorded so a second click fails. The failure message is identical for expired, used, unknown and tamperedA link forwarded, logged by an email gateway, or sitting in a shared inbox is dead by the time anyone else finds it
Sessions are signed and rotateThe cookie carries no data the server trusts without a signature check, and the identifier changes on use so a captured cookie has a short lifeSession fixation and long-lived stolen cookies are the two attacks a magic-link system is otherwise exposed to
Admin is an allowlist of addressesChecked at sign in against a list in configuration. Not a database row, not a flag, not a self-service upgradePrivilege escalation needs a deploy, which needs the repository, which is a different threat entirely
No public signupAn address that no admin has added receives the same neutral reply as one that does not exist. Adding a customer is an admin action, loggedDecision 16: high touch and white glove now, self serve later. The onboarding call is currently the product. The moment self serve arrives, this is the one switch that flips
What exists today

None of this. The only dashboard in the repository is a server-rendered page whose authentication is the runner token pasted into the query string, with a comment saying it is acceptable only on the local Mac. It renders the customer's connectors, runs, outputs, pending approvals, spend and brain, and it can approve or reject, which makes it a useful scaffold and an unshippable product. There is no sessions table, no magic-link table, no role and no admin console anywhere in the migrations or the code. This section is the specification for the thing that replaces it.

03The onboarding path, end to end

From an admin typing an email address to a crew running on schedules. Eight steps. The important part is not the happy path, it is what the product is when someone stops halfway, because most people will.

Why Telegram is step 7 and not step 2

Linking a chat is a thirty-second job and it is the difference between approvals arriving on a phone and approvals sitting unread in a browser tab. It belongs after the guardrails because the first thing that will ever arrive there is an approval request, and an approval request before the budgets are set is a question the owner cannot answer. The mechanism is already built: the dashboard mints a one-time code as an unverified channel row, the owner opens t.me/<bot>?start=<code>, and the bot swaps the code for the chat id and marks it verified, valid for twenty four hours. What is missing is a bot token.

04The Operator: the thing they actually talk to

It was described on the old version of this page as a runtime concept, a router with a personality. It is now the centre of the dashboard. The owner asks what happened, asks what the brain knows, tells an agent to go, changes a guardrail, approves work. Telegram is one channel into the same Operator, not a second product, and both channels reach the same code.

Its seven jobs, and the one thing each must never do

JobWhat it doesWhat it must never do
UnderstandClassifies intent from plain language against the entitled agents. "How did last week go" and "why are sales down" are the same intent with different urgencyGuess when ambiguous. Under 0.7 confidence it asks one clarifying question and dispatches nothing
AnswerReads the brain and the run log to answer "what happened", "what do we know about my customers", "why did we stop that ad". Every answer points at a run id or a dated brain lineAnswer from what it remembers of the conversation, or from the model's general knowledge. If it cannot point to a run or a brain entry, it says it does not know
PlanDecides whether this is one agent or several. "Launch my new serum" becomes Store Fix for the page, Ad Creative for the batch, Lifecycle for the launch flow, UGC Seeding for the first creators, Content for the announcement, in that order, with dependencies. A dependent run is dispatched when its parent completes, carrying parent_run_idRun a multi-agent plan without showing it first. Anything over one agent is previewed and needs an explicit yes
RouteDispatches through the same function every other trigger uses, with the brain sections that agent's manifest declares, and nothing elsePass one agent's raw output into another. Agents share state only through the brain
GateHolds the global guardrails above every agent's own: spend, concurrency, cooldown, message volume, who may approveLet a per-agent guardrail override a global one

It writes to the operations layer through the brain writer, exactly as the settings screen would, and reads the new value back to the owner for confirmationChange a guardrail silently, or change one that loosens a limit without the same confirmation the screen would demand. Loosening is a decision, not a preference
LearnWrites orchestration-level learnings to operations.operator_notes: what was asked, what was dispatched, what was declined. Dated linesWrite domain learnings. Those belong to the specialist that produced them, and to learnings.*, which is append only for everyone

Approving through the Operator

An owner can say "approve the creator deal" in chat. That reaches exactly the same decide() function as the Telegram button and the dashboard button, which is already built and already tested against tampered, replayed, expired and unknown tokens. The Operator does not hold the token and does not mint one. It resolves which pending approval the owner means, asks them to confirm if more than one is plausible, and hands the decision to the gateway, which mints a fresh single-use token bound to that customer and calls decide(). The database refuses a second use through a trigger, not only through code. There is no path in which chatting is a faster way to approve something than tapping the button.

What exists today

The Operator has a full specification and zero implementation. There is no OperatorDO and no CustomerDO in the Worker; the bindings the specification names do not exist in the Worker's environment type, which currently declares only the database and the bucket. What does exist, and works, is everything underneath it: the Telegram adapter with chat linking, /status and /approvals, inline approval buttons, the channel-agnostic decide path, and dispatch with entitlement, mode, cooldown and cap checks. The Operator is the missing layer between a sentence and that machinery.

One gap found in the code that the specification depends on. The Operator is specified to classify intent "against the list of entitled agents and their description fields". The manifest schema has no description field. Seventeen manifests have a name and nothing an intent classifier can read. This is the first entry in section 05's list of fields that have to be added.

05One cockpit renderer, sixteen configurations

Every agent needs a deep interface: its inputs, its schedule, its mode, its guardrails, its approval gates, its tools, its outputs, its history, and the handful of settings that agent alone has. Sixteen hand-built screens would look the same in week one and diverge by week four. So the manifest is the specification, the interface is generated from it, and a per-agent UI spec file adds the few things a manifest cannot express.

What the manifest carries today

Every one of the seventeen manifests validates against a single zod schema, and every field below already exists and is already read by running code. The renderer gets these for free.

The per-agent UI spec file

Some things do not belong in a manifest, because the runner has no use for them and a schema would turn into a stylesheet. Those live in spec/agents/<id>.md, one file per agent, which the coverage matrix already requires and which does not exist for any of the seventeen. It carries the owner-facing copy in the product's voice, panel order and any panel to suppress, the settings that genuinely belong to one agent alone, one worked example of a good output, and the plain-words explanation of every guardrail number. A new agent therefore ships with three files, manifest.json, AGENT.md and this one, and gets a complete interface without a line of interface code being written.

Five things this table tells you that no prose does

Only two agents have no approval gate at all and it is correct that they do not. Competitor Watch is read only and never contacts anybody. Weekly Brain Update is read only externally and never dispatches in autonomous mode. Everything else that touches money, a store or a person has between one and four gates.

Only two agents write anything other than learnings. Reviews writes customer objections and vocabulary, because the objections in a one-star review are the best customer research a store has and they belong where Ad Creative and Store Fix will read them. Social Engagement writes objections for the same reason. Everything else appends to learnings.* and nothing else, which is why the moat is a single append-only surface rather than sixteen competing edits.

Weekly Brain Update is the only writer of any performance section, and that is enforced by name in the brain writer, not by a prompt. If any other agent tries, the write is rejected and logged.

The per-run estimates are cents, not dollars. The most expensive single run in the system is Ad Creative at twenty five cents. The monthly figures in section 17 are large because of frequency, not because any one run is heavy. Post-Purchase costs three cents and runs every thirty minutes, which is the line worth watching.

Two agents have no schedule and are correct not to. Lifecycle builds the always-on flows once. Offer and Landing Page sets up one test at a time. Neither is a weekly rhythm, and neither should be woken by a cron.

Why Content Publishing does not cover retention

Content Publishing is acquisition-side: it makes reels and carousels that bring new people in. Retention is a different job with different data. It needs order history, segments and lifetime value, and its output is a campaign to people who already bought. Lifecycle builds the always-on flows once, welcome, cart, post-purchase. Retention and Winback is the operator who then uses that plumbing every week to decide who gets what. Plumbing against operator.

09The closed loop, and the one arrow nobody else has

This is the whole differentiation, drawn. Every brand brain on the market has a brain. Only one of them has agents that write back to it without a human remembering to.

10Self learning, made visible

Decision 15 says self learning is the moat, and marks it "active, needs a visible surface". Today learnings are written and nothing shows the owner what the brain learned, which means the most valuable thing the product does is the thing the customer cannot see. This section is the loop, precisely, and then how it is measured, so the claim is checkable rather than a slogan.

11The life of one request

What happens between "find me twenty skincare creators under two hundred dollars" arriving and the deals landing in the brain. The approval branch is the part that has to be right, and it is the part that is most thoroughly built.

One correction to how approval resumption works

The old version of this page drew approval as a pause that resumes the same run. The code does something cleaner and it is worth understanding, because it is the property that makes the runner safe to kill. On approval, the paused run is closed as complete and a new run is dispatched for the same agent, carrying resume_from and the R2 key of the exact payload that was approved, with the old run recorded as its parent. The runner holds no state between pulls. Kill the machine mid-run and exactly one run completes; nothing is half-applied, because the thing that executes on approval is a payload written to storage before the pause, not a variable in memory.

Two further details that are built and tested: the single-use rule is enforced twice, once by a conditional UPDATE that only matches a pending, unused row, and once by a database trigger that aborts any second write to token_used_at. And a result that cannot be posted back because the control plane is unreachable is retried four times with backoff and then spooled to disk, replayed on the next tick, because a finished run is expensive and throwing one away is not acceptable.

12Three modes, one agent, what actually changes

Mode is a field on every run, not a product tier. The same Creator Outreach agent file runs in all three. What changes is which tools the model is even shown, which actions pause, and who pulls the trigger.

The list that never relaxes

Nine actions are approval-gated regardless of mode, regardless of flags, and regardless of what an agent's own manifest says. Activating a Meta campaign, setting a Meta budget, publishing a Shopify theme, updating product content, setting metafields, enabling an email flow, sending an email campaign, and anything with send in its name in act mode. The ninth, closing a creator deal, is the only one with an escape hatch, and it is a per-customer flag that is off by default and stays off until the product owner says otherwise. An unknown tool name also fails closed and is gated, which is the correct default for a registry that will grow.

A correction on how modes were sold

The old version of this page mapped the three modes onto three one-time price tiers, with Advise running in the buyer's own ChatGPT for a one-time fee. The build plan's first line says hosted only, no one-time tiers, and lists that as a decision not to reopen. Both things are partly true and they need separating. Mode is a runtime field, per decision 2, and every hosted customer's agents move through modes as their connections and their confidence grow. The Advise-mode bundle is a separate artefact: it exists in the repository as a downloadable product with install guides, and the fulfilment path that classifies a payment, issues a single-use download link and emails it is built and tested. What no longer holds is the idea that a hosted agent's mode and a price tier are the same thing. They are not, and the price table lives in section 20's open questions because the specification and the decision log currently disagree about it.

13Where store data comes from

Three levels, and only the third is an integration. Each level unlocks specific agents, which is why data depth is a better upgrade story than a feature list. The level 3 mechanism has changed since this page was first written and the change is entirely in our favour.

Correction: how level 3 is actually reached

This page used to say the merchant creates a custom app in their own admin in five minutes and hands us a token. That path no longer exists. Shopify's own documentation now reads "You can no longer create new admin-created custom apps." The replacement is better for the merchant and slightly more work for us: we create one app per merchant in our developer dashboard with custom distribution, generate an install link for their store, and they click Install on a standard permissions screen. No app review, no protected-data review, no token copying, and a non-expiring offline token at the end of it. The client-credentials grant is not an alternative because it cannot reach a store outside our own organisation.

The OAuth start and callback are built and were exercised against a live staging store. The callback verifies the request signature, verifies the state we minted, exchanges the code, and then verifies that the scopes actually granted match the scopes requested, because a merchant can reduce them on the permissions screen. If any are missing, nothing is stored and the page says exactly which ones are absent.

Correction: theme writes are not a level 3 unlock

Level 3 was described here as unlocking theme writes. Live testing found otherwise: with write_themes granted, duplicating a theme returns "the user needs write_themes and an exemption from Shopify to modify themes". The scope alone is not enough for apps created now. So Store Fix's act mode writes content through scopes that are granted and tested: product descriptions and SEO fields, FAQ metafields, and unpublished draft pages. Theme code changes become developer recommendations naming the exact file, until an exemption exists. The three theme tools are still registered and still refuse to touch a theme whose role is main, waiting for the day the exemption arrives.

This is a cleaner product boundary than editing theme code ever was. Rollback is reverting a field, every change returns its previous value, and we never touch a merchant's code.

Why markdown, and how a run only loads what it needs

Markdown because the owner can read and edit it without a viewer, because it is the format every AI runtime already reads, and because a diff between two versions is legible to a human. The file is parsed into addressable sections keyed layer.section, and a manifest declares its reads as patterns: identity.*, customer.objections, module:market.sale_calendar, or * for the Weekly Brain Update which needs everything. Only the matching sections are rendered into the system prompt, so a run is cheap even when a brain has grown large. The brain is never cached between runs, which is what makes a correction take effect immediately rather than at the next restart.

There is no vector database and no semantic search. That was considered and rejected: add semantic recall when a real query fails without it, not before.

Ops alerts land in a chat that is already open on a phone. 17Estimated monthly run cost per agent

Why hosted is priced per agent and why Ad Creative carries a volume cap. These are estimates from the current pipelines' known costs, not measurements from customers who do not yet exist. Every run already records its real cost, so these bars start being replaced with facts on the first day of real traffic.

Two different cost numbers, and why both exist

The chart above is a monthly estimate per agent, built by multiplying an assumed schedule by an assumed run cost. The manifests carry a different number: cost_estimate_micro, the estimated cost of one run, in micro-USD. That one is not decoration. It is read by the dispatch function before a run row is inserted, added to the customer's spend so far today and this month, and compared against both caps. Over either cap the row is written with status over_cap, two events fire, and nothing executes. The per-run estimates range from three cents for Post-Purchase to twenty five cents for Ad Creative, and they are listed per agent in section 07.

How the estimates become facts

Every run posts back its real token counts and its real cost, which is written to a spend row against the customer, tagged by kind and provider. The loop also stops mid-run if accumulated spend crosses what remains of the cap, before the next model call rather than after it. So the mechanism that turns these bars into measurements is already running, and the only thing missing is traffic. One honest caveat: when the runner is using a local subscription rather than a metered API key, the reported cost is notional and the cap is deliberately not enforced against it. That is a development-only path and it is marked as such in the code.

18Infrastructure, as built

The control plane is Cloudflare. The execution plane is one Node process. The two are connected by nothing but HTTP and a table, which is the property that makes each of them replaceable. The one thing that has changed since this page was written is where that Node process runs today.

The repeatable playbook, per agent

  1. Define. Write the agent folder: AGENT.md with job, inputs, workflow, modes, output contract, quality gates, guardrails, what it cannot do, and resume handling. Then manifest.json with tools, gates and brain permissions. Then spec/agents/<id>.md, the UI spec, which no agent has yet.
  2. Register. The runner uploads every manifest to the control plane at boot, so the database's copy is never stale and never hand-edited.
  3. Implement its tools. This is the real work and the current bottleneck: 61 of the 75 declared tools do not exist. A tool is a schema, a mode list, a writes flag, an approval predicate, a spend estimate and an execute function returning a typed result.
  4. Run it. Locally against a fixture brain first, then against the one real store we are allowed to read, at level 1, in advise mode, with no writes ever.
  5. Prove it. Five real stores, output read and judged by a person. This is the only gate that cannot be automated and it is the one that matters.

After the first agent, steps 1 to 5 are the same shape every time, which is what turns thirteen remaining agents into a schedule instead of a project.

Cost control, before the first paying customer

Per-customer daily and monthly caps in micro-USD, checked at dispatch, before a run row is inserted. A run that would cross the cap is written as over_cap, two events fire, and nothing executes. The loop checks again mid-run and stops before the next model call if accumulated spend crosses what is left. Every run records its real cost against the customer. What is missing is the global daily cap across all customers, which is the last line of defence and is currently unwritten.
